# Profile runbook: Qwen checkpoint replay

Verify the exact first-class Qwen3 0.6B Q8_0 artifact, require accelerator
placement, admit caller-supplied text, and replay 16 greedy selections from one
checkpoint. This is the smallest end-to-end check of the model-profile
boundary; it does not add a chat template or interpret the generated text.

Source:
[`qwen_profile_replay.rs`](../../crates/runtime/examples/qwen_profile_replay.rs)

## Acquire and verify

Choose a model store outside the repository:

```sh
MODEL_STORE=/path/to/model-store
cargo run --quiet -p logit-loom-xtask -- models fetch \
  qwen3-0.6b-q8-0 --dir "$MODEL_STORE"
cargo run --quiet -p logit-loom-xtask -- models verify \
  qwen3-0.6b-q8-0 --dir "$MODEL_STORE"
```

The exact GGUF path is:

```sh
MODEL="$MODEL_STORE/qwen3-0.6b-q8-0/model/Qwen3-0.6B-Q8_0.gguf"
```

The fetch is opt-in and never runs from a test, package build, documentation
build, or CI job. It requests only the catalogued files at the pinned commit,
then checks the 639,446,688-byte GGUF against its SHA-256 digest.

## Run the profile loader

Select an accelerator backend compiled for the deployment:

```sh
cargo run --quiet -p logit-loom-runtime \
  --no-default-features --features vulkan \
  --example qwen_profile_replay -- \
  "$MODEL" "The creature opened its eyes and" \
  | tee qwen-profile-replay.json
```

`Loom::load_qwen3_small` verifies the catalog, byte count, and SHA-256 before
native loading and verifies the artifact again afterward. The caller still
supplies the path, backend feature, model placement, session allocation,
tokenization flags, prompt bytes, and generation plan.

## Inspect

Confirm exact profile identity, accelerator placement, and replay:

```sh
jq -e '
  .metadata.profile_artifact.profile_id == "qwen3-0.6b-q8-0"
  and .metadata.profile_artifact.sha256
    == "9465e63a22add5354d9bb4b99e90117043c7124007664907259bd16d043bb031"
  and (.metadata.devices | length) > 0
  and .input_bytes_hex == "546865206372656174757265206f70656e656420697473206579657320616e64"
  and .checkpoint.position == .first.receipt.initial_position
  and .checkpoint.position == .replay.receipt.initial_position
  and .exact_replay
' qwen-profile-replay.json
```

Then run the three focused experiments against the same verified path:

```sh
cargo run --quiet -p logit-loom-runtime --features vulkan \
  --example fork_and_jolt -- \
  "$MODEL" "The creature opened its eyes and" > qwen-fork-and-jolt.json

cargo run --quiet -p logit-loom-runtime --features vulkan \
  --example token_byte_microscope -- \
  "$MODEL" "The creature opened its eyes and" > qwen-token-bytes.json

cargo run --quiet -p logit-loom-runtime --features vulkan \
  --example exact_byte_stop -- \
  "$MODEL" "The creature opened its eyes and" 20 > qwen-byte-stop.json
```

The final command uses the exact byte `0x20` as its stop suffix. The report, not
an assumption about model text, determines whether that suffix was selected
within the bounded run.

## Mechanical success criteria

- `input_bytes_hex` records the exact caller-supplied UTF-8 prompt bytes for
  local inspection.
- The profile receipt names the pinned repository, revision, file, byte count,
  and SHA-256 without recording the local path.
- Native model devices contain an accelerator-class placement; the adapter
  never retries a rejected placement on CPU.
- Restoring the checkpoint yields identical token IDs, exact bytes, and
  generation receipts for the two greedy runs.
- Fork-and-jolt reports a completed transactional transform invocation.
- Token-byte microscope reconstructs the exact generated bytes from
  post-admission observations.
- Exact-byte stop either reports the selected suffix at its documented
  boundary or honestly exhausts its declared token bound.

Input and generated bytes remain outside the checked-in acceptance record. A
replay or output difference establishes mechanics for this run only.
