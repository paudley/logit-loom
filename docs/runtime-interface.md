# Higher-level runtime interface

`logit-loom-runtime` is the convenience layer for direct local llama.cpp use.
It composes the existing contracts, transform runtime, and adapter without
reinterpreting their mechanics.

The façade removes repetitive ownership and call wiring. It deliberately does
not hide choices that affect execution: model path, native backend feature,
device policy, session allocation, exact prompt text, tokenization flags,
generation bounds, transforms, observers, steering resources, and checkpoint
compatibility remain caller-visible.

## Layer selection

| Requirement | Start with |
| --- | --- |
| Load one local model and run explicit generation workflows | `logit-loom-runtime` |
| Store or exchange backend-neutral plans and receipts | `logit-loom-core` |
| Execute transforms and observers against another backend | `logit-loom` |
| Manage llama.cpp runtime, model, and session ownership separately | `logit-loom-llamacpp` |

The lower layers remain public and unchanged. The runtime crate re-exports the
backend-neutral `logit-loom` surface and provides `low_level` module aliases
when an application needs to cross the façade boundary intentionally.

## Ownership

```text
Loom
  ├─ loaded Model
  ├─ initialized native Runtime
  └─ default LoomOptions
       │
       └─ LoomSession<'loom>
            └─ one mutable causal Session<'model>
```

`Loom` keeps the loaded model alive until before native runtime shutdown.
`LoomSession` borrows that owner and retains the adapter's single-owner,
neither-`Send`-nor-`Sync` session contract. The crate is synchronous and does
not create a worker, executor, queue, or hidden lock. Applications can place
the complete owner in their own single-owner worker when they need concurrent
request handling.

The native binding permits one process runtime owner. `Loom::load` is therefore
the direct one-model path. Applications that need several model objects under a
separately managed runtime should use `logit-loom-llamacpp`.

## One-shot and stateful calls

`Loom::complete` creates a fresh session using the configured
`SessionOptions`, admits exact caller text as replacement state, performs one
bounded generation request, and drops the session. Its output retains both
prompt-admission accounting and the generated bytes, tokens, and receipt.

`Loom::session` exposes the stateful path:

- `replace_text` clears prior causal state before admitting the tokenized text;
- `append_text` admits the tokenized text after existing causal state;
- the `_observed` variants invoke a caller-owned `PrefillMonitor` at complete
  prefill chunk boundaries;
- `generate` operates on the current causal state;
- `clear`, `capture_state`, and `restore_state` preserve the adapter's failure
  and compatibility behavior.

A cooperative controlled-prefill stop is a successful partial admission, not
an execution error. Inspect `AdmissionOutput::prefill` before starting
generation; the output's token vector records the complete tokenizer result
while `PrefillOutput::admitted_tokens` records the admitted prefix.

Text methods accept UTF-8 because they call the model tokenizer. Generated
token pieces and complete output remain arbitrary bytes. `CompletionOutput`
and `GenerationOutput` expose those bytes directly; text conversion is
fallible.

No method formats a conversation, selects a template, inserts a role, or adds a
system prompt. A caller that wants those semantics must render the exact text
before admission.

## Generation controls

`GenerationRequest` owns one validated, serializable `GenerationPlan` and may
borrow one mutable `Pipeline` and one mutable `ObserverSet` for the synchronous
call. This makes the durable contract separable from process-local callbacks.

The builder methods retain the lower-level ordering:

1. observer polling occurs at the pre-sampling boundary;
2. ordered Rust transforms run against copied candidate logits;
3. changes commit only if every stage succeeds;
4. native grammar, logit bias, penalties, filters, temperature, and terminal
   sampling run afterward;
5. a nonterminal selection enters native causal state;
6. transforms and observers receive the admitted token;
7. exact byte stop suffixes are checked.

`GenerationRequest::bias` configures native logit bias at step 4.
`PipelineBuilder::token_bias` creates an ordered Rust transform at step 2.
Their names are similar, but their execution boundaries are intentionally
different.

`PipelineBuilder` requires a candidate exposure mode and positive maximum call
count up front. Its stages share those bounds. Applications requiring
per-stage exposure or bounds can build the lower-level `Pipeline` directly.

## Implementation identities

Mechanical receipts bind transform and observer implementation identities.
The façade assigns identities only when it can describe the implementation and
configuration itself:

| Helper | Identity domain |
| --- | --- |
| `PipelineBuilder::rank_bias` | `runtime-rank-bias-v1` |
| `PipelineBuilder::token_bias` | `runtime-token-bias-v1` |
| `ObserversBuilder::cancellation` | `runtime-cancellation-observer-v1` |

Rank and bias identities bind exact finite floating-point bits. Token-bias
identities bind the normalized last-value-wins map in ascending token order.
The enclosing transform specification separately binds candidate exposure and
the call bound.

Custom transforms, callbacks, and observers require a caller-supplied `Digest`.
The caller must advance its identity domain or configuration bytes whenever
the callback's mechanics change. The crate cannot derive a stable
implementation identity from arbitrary Rust code.

`Loom::model_identity`, `Loom::backend_identity`, and
`Loom::backend_compatibility` expose the content/build identities used by
checkpoint validation. They are mechanical compatibility data, not claims
about model behavior.

## Checkpoints

Checkpoint helpers are available only on an unsteered `LoomSession`.
`capture_state` returns opaque native state with exact token lineage and a
receipt bound to:

- the loaded GGUF bytes;
- the adapter and native build identity;
- exact context, batch, micro-batch, and thread options;
- state bytes, token history, and causal position.

`restore_state` revalidates those fields before native restoration. A snapshot
is suitable for branching or resuming within a controlled compatible
deployment; it is not a portable model-state file format.

## Steering

`LoomSession::lora` and `LoomSession::control_vector` return distinct typed
sessions for the active resource. Their generation and exact-text admission
methods preserve the ordinary boundaries, while checkpoint methods are absent
so a snapshot cannot silently omit active steering state.

Call `clear` to observe cleanup and receive its lifecycle receipt. Dropping a
scope still attempts cleanup. A failed cleanup poisons the underlying session,
and later mutation reports the retained failure instead of continuing with
unknown native state.

These are caller-selected mechanical resources. The interface does not attach
semantic policy or efficacy claims to either mechanism.

## Validation boundary

Ordinary workspace tests compile the complete adapter and exercise model-free
builder, identity, exact-byte, callback, accounting, and bounds behavior. They
do not load or download a model. The `generate` and `branch` examples are
compile-tested and execute only when a caller supplies a local GGUF and an
explicit backend feature.
